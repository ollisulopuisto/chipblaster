# Bolt's Performance Journal

## 2026-11-09 - Memoizing playlist queue selection and index resolution against position ticks
**Learning:** In applications where audio playback intervals trigger React component re-renders (such as the 250ms position timer in `App.tsx`), evaluating playlist queue selection via successive `Array.prototype.find` and `Array.prototype.indexOf` calls (`queueRows.find(t=>t.id===selQueueId) ?? queueRows.find(t=>t.id===activeQueueId) ?? queueRows[0] ?? null` and `queueRows.indexOf(queueSel)`) causes multiple unmemoized $O(N)$ linear scans on every render tick. For a playlist of 250 items, executing this inline across 20,000 render ticks consumes ~52–108ms in V8. Wrapping the resolution in `React.useMemo(() => ..., [queueRows, selQueueId, activeQueueId])` with a single index resolution pass avoids redundant traversals between queue mutations, reducing 20k render checks to ~0.02–0.33ms (~600x speedup) and eliminating unnecessary function call overhead on high-frequency playback ticks.
**Action:** When component re-renders occur at high frequency, memoize active/selected item and index resolutions over user playlists and list collections against selection and collection changes with `React.useMemo`.

## 2026-11-08 - Memoizing track duration parsing against high-frequency playback position ticks
**Learning:** In applications where audio playback intervals trigger React component re-renders (such as the 250ms position timer in `App.tsx`), evaluating track duration in an unmemoized IIFE causes regex evaluations (`/^(\d+):(\d+)/`), metadata dictionary lookups (`metadata.lengths[sharePath]?.[subtune]`), and string-to-number parsing on every tick. Across 50,000 render iterations, computing this inline consumes ~13–27ms in V8 (~150–205ms in Python reference runs) and creates temporary regex match arrays. Wrapping `knownLength` in `React.useMemo(..., [sharePath, subtune, chipLoaded, catalogReady])` avoids redundant regex execution and metadata dictionary scans while the track is playing, reducing 50k render checks to ~0.3–1.1ms (~17–45x speedup in JS, >34x in Python benchmark) and eliminating GC churn during continuous playback.
**Action:** In components driven by sub-second playback/animation timers, memoize metadata lookups and regular expression parsing over active media tracks with `React.useMemo` against the track and subtune identifiers.

## 2026-11-07 - Using memoized queue partition lengths for transport skip button disabled states
**Learning:** In applications where high-frequency render loops occur (such as 250ms playback position updates), evaluating transport button disabled states using nested linear scans (`playedIdsRef.current.some(id => id !== activeQueueId && queueBanks[chipSource].some(t => t.id === id))` and `queueBanks[chipSource].some(t => t.id !== activeQueueId && !playedIdsRef.current.includes(t.id))`) causes $O(P \times Q)$ traversals on every render. Because `queueGroups` already partitions the playlist tracks into played and upcoming lists, checking `!queueGroups[0].tracks.length` and `!queueGroups[2].tracks.length` provides an exact $O(1)$ replacement, slashing evaluation time from ~220ms down to ~1.3ms per 20k renders (~170x faster) without allocating temporary collections or state.
**Action:** When determining navigation/boundary availability for list collections that are already partitioned into memoized groups, query the memoized group lengths directly rather than re-running nested linear array scans in JSX attributes.

## 2026-11-06 - Memoizing Set of collection identifiers for high-frequency render lookups
**Learning:** When components re-render at high frequency (such as 250ms playback position updates), performing multiple `Array.prototype.includes` checks across multiple rendered lists, buttons, and aria-labels against user collection arrays (e.g., favorites lists with 50–500 items) degrades rendering performance due to repeated $O(M \times N)$ linear traversals (consuming 100–740ms per 10k renders). Creating and memoizing a `Set` (`React.useMemo(() => new Set(favorites), [favorites])`) allows $O(1)$ membership checks (`set.has`) across all JSX elements, reducing lookup time from ~236ms to ~12ms per 10k renders (~20x speedup for 150 items, >50x for larger collections) and avoiding redundant `Set` construction inside downstream filtered memoizations.
**Action:** Memoize identifier sets with `React.useMemo` whenever multiple collection membership checks exist across rendered elements in components updated by high-frequency intervals.

## 2026-11-05 - Memoizing active track index over large catalog arrays
**Learning:** In applications where high-frequency timer intervals (such as a 250ms audio position ticker) trigger React component re-renders, computing button disabled states directly in JSX using linear searches (`Array.prototype.indexOf`) over massive static arrays (~61k entries) forces $O(N)$ string traversals on every render cycle. When playing tracks toward the middle or end of the catalog, running multiple `paths.indexOf(sharePath)` checks consumes ~0.2–0.4ms of CPU time per render (~1.9s per 10k renders). Memoizing `sharePathIndex` via `React.useMemo` against the active track (`sharePath`) and catalog readiness eliminates repetitive array scans, dropping 10k render checks from ~1,900ms to ~0.4ms (>4000x faster) without allocating temporary state.
**Action:** When component re-renders are driven by high-frequency intervals, never call `indexOf` or other linear search methods over large static collections in JSX props; memoize the item index against collection and active item changes.

## 2026-11-04 - Single-pass playlist queue partitioning with Set lookup and memoization
**Learning:** Partitioning playlist queues during React renders using multi-pass `.map().filter()` with `Array.prototype.includes` results in $O(N \times M)$ linear searches and repeated intermediate array/object allocations. When playback timer intervals (250ms) cause component re-renders, unmemoized queue grouping causes unnecessary garbage collection pressure and main thread stalls. Pre-populating a `Set` for $O(1)$ membership and partitioning tracks into groups in a single loop cuts execution time by ~8.9x (from 620.46ms to 69.90ms per 10k ops) and eliminates redundant work between queue state changes via `React.useMemo`.
**Action:** When categorizing/partitioning collections for list rendering, use a `Set` for ID lookups, partition in a single pass, and memoize against high-frequency timer state changes.

## 2026-11-01 - Single-pass catalog directory partitioning with memoization
**Learning:** In catalog directory navigators holding large static path sets (~61k entries), multi-pass chained array transforms (`.map().filter().map()`) create hundreds of thousands of intermediate string slices and array objects (~360 KB/op). Furthermore, performing unmemoized array filtering inside the main React component body re-executes on high-frequency interval updates (such as audio player position updates every 250ms), stealing 2.6ms of frame budget. Combining directory extraction and visible item partitioning into a single linear loop with index-based slash search (`p.indexOf('/', baseLen)`) and memoizing via `useMemo` reduces navigation latency from ~30ms to ~2.6ms (~11x speedup) and cuts memory churn by 97.5%.
**Action:** Replace chained `.map().filter()` directory parsers over large path lists with a single loop partitioning both folders and items, and ensure all derivations over large collections are memoized against high-frequency timer renders.

## 2026-05-18 - Pre-normalizing large static search catalogs
**Learning:** In browser catalog/library search interfaces with large datasets (~61k strings), executing Unicode normalization (`s.normalize('NFD')`) and regex transforms on every keystroke in React component render cycles blocks the UI thread for ~50ms+. Pre-normalizing paths once when catalog data arrives cuts per-keystroke search latency from ~55ms down to ~7-12ms (~5-8x speedup).
**Action:** Always pre-normalize static text datasets during initial load/worker ingest rather than running string normalizations repeatedly inside search/filter loops.
