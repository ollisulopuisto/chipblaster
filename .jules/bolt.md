# Bolt's Performance Journal

## 2026-11-05 - Memoizing active track index over large catalog arrays
**Learning:** In applications where high-frequency timer intervals (such as a 250ms audio position ticker) trigger React component re-renders, computing button disabled states directly in JSX using linear searches (`Array.prototype.indexOf`) over massive static arrays (~61k entries) forces $O(N)$ string traversals on every render cycle. When playing tracks toward the middle or end of the catalog, running multiple `paths.indexOf(sharePath)` checks consumes ~0.2–0.4ms of CPU time per render (~1.9s per 10k renders). Memoizing `sharePathIndex` via `React.useMemo` against the active track (`sharePath`) and catalog readiness eliminates repetitive array scans, dropping 10k render checks from ~1,900ms to ~0.4ms (>4000x faster) without allocating temporary state.
**Action:** When component re-renders are driven by high-frequency intervals, never call `indexOf` or other linear search methods over large static collections in JSX props; memoize the item index against collection and active item changes.

## 2026-11-04 - Single-pass playlist queue partitioning with Set lookup and memoization
**Learning:** Partitioning playlist queues during React renders using multi-pass `.map().filter()` with `Array.prototype.includes` results in $O(N \times M)$ linear searches and repeated intermediate array/object allocations. When playback timer intervals (250ms) cause component re-renders, unmemoized queue grouping causes unnecessary garbage collection pressure and main thread stalls. Pre-populating a `Set` for $O(1)$ membership and partitioning tracks into groups in a single loop cuts execution time by ~8.9x (from 620.46ms to 69.90ms per 10k ops) and eliminates redundant work between queue state changes via `React.useMemo`.
**Action:** When categorizing/partitioning collections for list rendering, use a `Set` for ID lookups, partition in a single pass, and memoize against high-frequency timer state changes.

## 2026-11-01 - Single-pass catalog directory partitioning with memoization
**Learning:** In catalog directory navigators holding large static path sets (~61k entries), multi-pass chained array transforms (`.map().filter().map()`) create hundreds of thousands of intermediate string slices and array objects (~360 KB/op). Furthermore, performing unmemoized array filtering inside the main React component body re-executes on high-frequency interval updates (such as audio player position updates every 250ms), stealing 2.6ms of frame budget. Combining directory extraction and visible item partitioning into a single linear loop with index-based slash search (`p.indexOf('/', baseLen)`) and memoizing via `useMemo` reduces navigation latency from ~30ms to ~2.6ms (~11x speedup) and cuts memory churn by 97.5%.
**Action:** Replace chained `.map().filter()` directory parsers over large path lists with a single loop partitioning both folders and items, and ensure all derivations over large collections are memoized against high-frequency timer renders.

## 2026-05-18 - Pre-normalizing large static search catalogs
**Learning:** In browser catalog/library search interfaces with large datasets (~61k strings), executing Unicode normalization (`s.normalize('NFD')`) and regex transforms on every keystroke in React component render cycles blocks the UI thread for ~50ms+. Pre-normalizing paths once when catalog data arrives cuts per-keystroke search latency from ~55ms down to ~7-12ms (~5-8x speedup).
**Action:** Always pre-normalize static text datasets during initial load/worker ingest rather than running string normalizations repeatedly inside search/filter loops.
